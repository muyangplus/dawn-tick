## 0. 结论先行（三句话）

1. **「桌面小组件」是本次选型的决定性约束**：微软官方明确 **只有 MSIX 打包应用才能注册为 Windows 11 小组件提供程序**（原文见 1.1）。
2. 因此 **Electron / Tauri 这类非 MSIX 应用做不到 Win11 小组件面板**；**Flutter 没有官方路径**；**React Native/Expo 根本没有 Windows 桌面平台**。
3. **最稳妥的方案是「Windows 用 C#/WinUI 3 原生（官方一等路径）+ Android 用 Kotlin/Glance（官方一等路径）+ Web 用 React」**——代价是 Windows 端不与 Web 共用 UI 代码。

### 1.1 最关键的一条官方原文

> **"In the current release, only packaged apps can be registered as widget providers."**
> —— [Implement a widget provider in a C# Windows App](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs)（同句亦见于 [C++/WinRT 版](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-win32)，两页均为 2026-08-19 更新）

配套硬性要求（同一教程确证）：

- 需要 **Windows App SDK ≥ 2.3.1**；
- 需要实现 COM 接口 `IWidgetProvider` / `IWidgetProvider2` 并注册类工厂；
- 需要在 `Package.appxmanifest` 声明 `com:Extension` + `uap3:Extension`；
- 小组件的 UI **不是任意 UI 框架**，而是 [Adaptive Cards JSON 模板](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widgets-create-a-template)（也支持 [HTML-from-URL](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/web-widget-providers)，但 provider 仍须 MSIX）；
- **不必须上架 Microsoft Store**——必需的是「MSIX + 可信签名」，[sideload 亦可](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/guides/tauri)（需自签名证书，用户需信任它一次）。

### 2.1 补充：B 方向的小组件「救回路径」细节

`tauri-plugin-widgets`（MIT，社区作者 s00d，**非官方**）的 Windows 做法正是上面推断的架构：
`npx tauri-plugin-widgets-api init-windows` 会把一份 **C# `IWidgetProvider`** 生成到 `src-tauri/windows-widget/`，
Rust 宿主把 Adaptive Cards JSON 写入共享存储，C# provider 读后喂给小组件面板
（[Windows setup 文档](https://s00d.github.io/tauri-plugin-widgets/guide/setup/windows)）。
该页也提供「Desktop webview fallback」（即悬浮窗）与 `workerw` 壁纸挂载作为退路。

**风险（我必须如实说）**：这是**单人社区项目**，其 star 数、发布日期、npm 版本与生产就绪度**本次未能确证**。
选 B 就意味着：小组件这个核心卖点，押在一个未经充分验证的社区插件上，且你要同时维护 Rust + C# 两条工具链。

|---|---|---|

If the computer is turned off during the scheduled delivery time, and remains off for longer than 5 minutes, the notification will be **'dropped'**." 官方建议改用 time-trigger 后台任务（[来源](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled)、[后台任务](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/applifecycle/background-tasks)） | **笔记本电脑合盖/关机后，课前提醒可能丢失**。这是「课前准时提醒」这个核心卖点的真实缺口，任何 Windows 方案都要处理 |

### 9.1 「Capacitor(Android) + Tauri 2(Windows) 是否更合适」— 是的，依据如下

按负责人要求核实了官方文档，结论是**这个组合优于「Tauri 2 一套壳打通 Windows + Android」**：

| 维度 | Tauri 2（覆盖两端） | Tauri 2(Windows) + Capacitor(Android) |
|---|---|---|
| **Android 定时提醒** | ❌ Tauri 官方[通知插件](https://v2.tauri.app/plugin/notification/)的文档只有「发送通知/动作/附件/频道」，**没有定时 API** → 需自己写 Kotlin 插件 | ✅ Capacitor 官方 [`@capacitor/local-notifications`](https://capacitorjs.com/docs/apis/local-notifications) 提供 `schedule()`，且文档化了 `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`、Doze 下 `allowWhileIdle`、以及精确闹钟被用户关闭时的检测与降级 |
| **Android 本地 SQLite** | ✅ [tauri-plugin-sql](https://v2.tauri.app/plugin/sql/) 平台表含 android，且插件自带迁移 API | ✅ `@capacitor-community/sqlite` |
| **Android 主屏小组件** | ⚠ 需写原生 Kotlin | ⚠ 同样需写原生 Kotlin（**打平**） |
| **Windows 壳能力** | ✅ 官方[托盘](https://v2.tauri.app/learn/system-tray/)、[开机自启](https://v2.tauri.app/plugin/autostart/)插件，体积小 | ✅ 同为 Tauri 2 |
| **维护成本** | 一个壳配置 | ⚠ 两套壳、两条构建链（Rust 与 Android SDK） |

**判断依据**：Android 端最核心的功能是「课前准时提醒」，Capacitor 有**官方且文档完备**的定时通知方案，
而 Tauri 在 Android 上要自己写 Kotlin 插件；而小组件两边都得写原生 Kotlin，所以「一壳打通」的优势被抵消。
→ **选 Capacitor(Android) + Tauri 2(Windows)。**

### 9.3 这个组合带来的三条硬约束（须写进实现规范）

1. **两套壳的插件 API 必须用一层平台适配层隔离**，否则业务代码会被绑死在某一端。
2. **Windows 必须常驻托盘**（D29）——Tauri 官方通知插件在 Windows 仅对"installed apps"生效且不支持定时，
   靠常驻进程自己算时间是最可靠路径；同时必须做开机自启，否则用户重启后收不到提醒。
3. **Android 必须如实申报 `USE_EXACT_ALARM`**（课表/日历属官方认可的核心功能场景），
   否则 Android 14+ 精确闹钟默认被拒，提醒会不准。
