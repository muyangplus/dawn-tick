## 5. 本次校验**未能**覆盖的部分（别把「39 项通过」当成全部验证完）

| 未覆盖 | 原因 |
|---|---|
| **三端 SQLite 能力一致性** | 本校验只跑了桌面 Python 的 SQLite 3.50.4。**Web(WASM) / Tauri(sqlx) / Capacitor 各自的 SQLite 版本尚未验证**（风险 R11）。当前模型刻意只用标准语法降低风险，但 M1 必须三端各跑一次同一份 DDL |
| **「展开(expand)」逻辑** | 把排课规则展开成具体课次并叠加放假/调休/调课，属 M2 工作（`01` 第 6 节），是项目最复杂的一段 |
| 「下一节课」查询与性能 | 需 `time_slots × start_date` 计算绝对时刻 |
| ICS 导入导出往返一致性 | 见 `03-开源组件调研.md` 第 2 节（单双周必须设 `WKST`） |
| 真实教务系统导出的畸形数据 | 需要真实样例文件 |
| 迁移脚本（`001_init.sql` 等）与版本号推进 | M1 处理 |
| 并发写入 | M1 处理 |

## 6. 结论

1. 数据模型 **v3（定稿）技术可行性已验证：39/39**，含负责人决定的「单表承载 7 种语义」方案。
2. **本次校验纠正了两处自己的错误**（见下），说明这一步值得做：
   - v1 的 `custom` 周次分支写成「不过滤」，会导致自定义周次课程在所有周显示；
   - v3 起初把来源优先级当成「查询时在多行里挑」，与「每天只能一条」的唯一索引自相矛盾，
     已纠正为**写入时的覆盖决策**。
3. **剩余最大不确定性是三端 SQLite 能力差异（R11）**，须在 M1 用同一份 DDL 在三端各跑一次。
4. 第 3 节样例建议直接转为正式单元测试。
5. 校验脚本在 `tools/schema-check/`（非产品代码），建议保留为正式测试基础。
