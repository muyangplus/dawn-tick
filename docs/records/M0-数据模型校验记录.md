## 3. 这次校验验证了什么（关键结论）

| 结论 | 意义 |
|---|---|
| 10 张表的 DDL 可执行，含 CHECK / 外键 / 部分唯一索引（`WHERE` 条件的唯一索引）语法均被 SQLite 接受 | 草案**可以直接转成正式建表脚本**，不需要换数据库 |
| 「每用户只有一个当前学期」靠**部分唯一索引**在数据库层强制 | 不依赖应用层自觉，杜绝「两个当前学期」这种脏数据 |
| **单双周判定**（`week_type` + `week % 2`）查得准 | 「单双周」需求已证实可实现 |
| **自定义周次（碎片规则）查得准** | 用 `json_each` 实测：第 5/7 周命中、第 6 周不命中，见下方第 4 节的**重要发现** |
| **周次位图方案同样正确** | `[1,3,5,7]` → `mask=85`，且**不需要 JSON 函数**，兼容性更好 |
| 周次范围越界（第 17 周 > 16 周）自动无课 | 期末周不会误显示课程 |
| 软删除后重建同节次记录不被唯一索引挡住（风险 R3） | 已实测，不需要为它设计额外规避方案 |
| 删除课程级联清理排课 | 风险 R4 中「幽灵数据」的一半已被数据库解决（**提醒表仍无外键，需应用层处理**） |

## 4. 重要发现（本次校验暴露/澄清的问题）

### 4.1 草案原有的 `custom` 分支是错的（已修正）

草案第一版里 `week_type = 'custom'` 因为写成「不过滤」，等于**自定义周次课程在所有周都会显示**。
这次校验把样例数据加进去才发现。现已改为：

```sql
OR (s.week_type = 'custom'
    AND EXISTS (SELECT 1 FROM json_each(s.weeks) WHERE json_each.value = :week))
```

并加上「第 5/7 周命中、第 6 周不命中」三项断言，防止将来回归。

> 说明：这个问题是**跑起来才发现的**，也正说明为什么值得先做这一步校验再定稿。

### 4.2 JSON 方案的平台隐患 → 位图方案作为备选（对应风险 R7）

`json_each` 属于 SQLite 的 JSON 函数族。SQLite 3.38+ 默认启用，桌面/Web 端没问题；
但 **Android 系统自带的 SQLite 版本与编译选项因系统版本而异**，不能假设一定可用。

因此本次额外实测了**位图整数**方案：把「上哪几周」压成一个 30 位整数，查询用
`(weeks_mask >> (:week - 1)) & 1 = 1`。结果：`[1,3,5,7]` → `mask=85`，6 项正反例全部判定正确，
且**完全不依赖 JSON 函数**。

**结论：若你选择「周次集合」路线，位图比 JSON 更稳。** 请在 `01` 的 **Q-A2** 上做选择。
