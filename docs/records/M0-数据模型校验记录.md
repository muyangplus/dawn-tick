## 3. 这次校验验证了什么（关键结论）

| 结论 | 意义 |
|---|---|
| 10 张表的 DDL 可执行，含 CHECK / 外键 / 部分唯一索引（`WHERE` 条件的唯一索引）语法均被 SQLite 接受 | 草案**可以直接转成正式建表脚本**，不需要换数据库 |
| 「每用户只有一个当前学期」靠**部分唯一索引**在数据库层强制 | 不依赖应用层自觉，杜绝「两个当前学期」这种脏数据 |
| **单双周判定**（`week_type` + `week % 2`）在 JSON/自定义周次混合下查得准 | 你需求里的「单双周」已被证实可实现，见下方第 4 节样例 |
| 周次范围越界（第 17 周 > 16 周）自动无课 | 期末周不会误显示课程 |
| 软删除后重建同节次记录不被唯一索引挡住（风险 R3） | 已实测，不需要为它设计额外规避方案 |
| 删除课程级联清理排课 | 风险 R4 中「幽灵数据」的一半已被数据库解决（**提醒表仍无外键，需应用层处理**） |

### 校验用的样例数据（建议作为将来单元测试的固定样例）

|---|---|---|

| 并发写入 / 数据迁移 | M1 处理 |

## 5. 结论与建议

1. 数据模型**技术可行性已验证**，可以进入定稿评审。
2. `custom` 周次分支必须先定下来（对应 `01` 的 **Q-A2**，我建议甲方案为主 + `weeks` 字段兜底，并在 M2 补齐 `json_each` 查询）。
3. 本文件中的样例数据建议直接转为 M1/M2 的单元测试用例，防止「单双周 + 周次范围」回归。
