### 2.5 `course_schedules` 排课 — ✅ 需求已给（课程、星期、节次、周次范围、教室）

**这是整个模型里最关键、也最容易出错的一张表。**

```sql
CREATE TABLE course_schedules (
  id           TEXT PRIMARY KEY,
  course_id    TEXT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  day_of_week  INTEGER NOT NULL CHECK (day_of_week BETWEEN 1 AND 7), -- 1=周一
  period_start INTEGER NOT NULL CHECK (period_start BETWEEN 1 AND 20),
  period_end   INTEGER NOT NULL CHECK (period_end   BETWEEN 1 AND 20),
  week_start   INTEGER NOT NULL DEFAULT 1  CHECK (week_start BETWEEN 1 AND 30),
  week_end     INTEGER NOT NULL DEFAULT 20 CHECK (week_end   BETWEEN 1 AND 30),
  week_type    TEXT NOT NULL DEFAULT 'all'
                 CHECK (week_type IN ('all','odd','even','custom')), -- ⚠ 见 Q-A2
  weeks        TEXT,                         -- week_type='custom' 时的周次集合，JSON：[1,3,5]
  room         TEXT,                         -- 覆盖 courses.location
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER,
  CHECK (period_end >= period_start),
  CHECK (week_end  >= week_start)
);

CREATE INDEX ix_schedules_course ON course_schedules(course_id);
CREATE INDEX ix_schedules_day    ON course_schedules(day_of_week);
```

> **Q-A2 是本模型最需要你拍板的点**，三条路线（均已实测，见 `records/M0-数据模型校验记录.md`）：
> - **甲（字段式）**：`week_start` + `week_end` + `week_type`(全周/单周/双周/自定义)。直观、贴近学校教务表述，但「上 3-5 周 + 上 8-12 周的双周」这种碎片规则要拆成多行。
> - **乙（JSON 集合）**：统一存实际周次集合（JSON 数组），任何碎片规则都是一行，用 `json_each` 查询。**已实测可查准**（第 5/7 周命中、第 6 周不命中）。**但依赖 SQLite 的 JSON 函数**——Android 系统自带 SQLite 的版本与编译选项各不相同，若不打包自带 SQLite 就存在隐患。
> - **丙（位图整数）**：同样存「实际周次集合」，但压缩成一个 30 位整数，查询条件为 `(weeks_mask >> (:week - 1)) & 1 = 1`。**已实测正确**（`[1,3,5,7]` → `mask=85`），且**完全不依赖 JSON 函数**，任何 SQLite 版本都能跑。
> - 我倾向 **甲为主 + `weeks` 兜底**（即当前草案）；若你更看重「碎片规则一行搞定」，则**丙（位图）比乙（JSON）更稳**。

⚠ 其他待确认：
- Q-A9：学校是否有「单双周从第几周起算」的特殊定义？
- Q：一门课一周上多次（周一 1-2 节 + 周三 3-4 节）是否就是两行？→ 我按**是**设计。
- Q：是否需要「连堂显示为一块」的合并逻辑（同课程相邻节次）？属于渲染层，默认做。

## 4. 关键查询（用来验证模型是否够用）

> 如果这几条 SQL 写得别扭，说明模型需要改。**这是检验设计的主要手段。**

```sql
-- Q1. 查「第 N 周某天」的课程（周视图一格一格渲染用）
--     注意 week_type 单双周与 custom 集合的判定
SELECT c.name, c.color, s.period_start, s.period_end, COALESCE(s.room, c.location) AS room
FROM course_schedules s
JOIN courses c ON c.id = s.course_id
WHERE c.semester_id = :semester_id
  AND s.day_of_week = :dow
  AND :week BETWEEN s.week_start AND s.week_end
  AND ( s.week_type = 'all'
     OR (s.week_type = 'odd'  AND :week % 2 = 1)
     OR (s.week_type = 'even' AND :week % 2 = 0)
     OR (s.week_type = 'custom'
         AND EXISTS (SELECT 1 FROM json_each(s.weeks) WHERE json_each.value = :week)) )
  AND s.deleted_at IS NULL AND c.deleted_at IS NULL;

-- Q2. 「下一节课」（小组件用）：今天还没开始的最近一节 + 明天的第一节
--     需要先由 periods 表算出每节的绝对时刻，再和 now 比较

-- Q3. 某天是否放假（提醒是否跳过）
SELECT kind, as_day_of_week FROM day_overrides
WHERE semester_id = :sid AND date = :date AND deleted_at IS NULL;
```

⚠ **Q2 暴露一个设计点**：`course_schedules` 里没有「绝对时刻」，必须结合 `semesters.start_date` + `time_slots` 计算。
「下一节课」的查询会频繁调用，建议在应用层做一个**展开(expand)函数**：把排课规则展开成一段日期区间内的具体课次（occurrence），供课表渲染、提醒调度、小组件共用。是否需要**缓存展开结果**到一张 `occurrences` 表（换取查询速度、付出失效复杂度）？→ ⚠ 待你决定，我倾向**先不落库，纯函数展开**。

## 5. 我自己发现的风险（需要你知晓）

| # | 风险 | 说明 |
|---|---|---|
| R1 | 周次与节次的「1 起算 vs 0 起算」 | 全项目必须统一为 1 起算，否则导出/导入来回一次就错位。建议写进代码规范。 |
| R2 | 时区 | 全部按设备本地时区（Asia/Shanghai）存墙钟时间，**不要存 UTC 时刻**，否则跨时区/夏令时出错。你要求多端同步，需在同步协议里明确「墙钟时间 + 时区」语义。 |
| R3 | 软删除 + 唯一索引冲突 | 软删除后重建同名记录会撞唯一索引（如 `ux_time_slots`），需在恢复逻辑里处理。 |
| R4 | `reminders.target_id` 无外键 | 删除课程不会级联删提醒，必须在应用层保证；否则将来出现「幽灵提醒」。 |
| R5 | 提醒的精确性依赖系统能力 | 见 `02-技术选型对比.md`，Android 精确闹钟权限 / 应用关闭后能否提醒，会直接限制「课前准时提醒」这个核心卖点。 |
| R6 | 「单双周 + 周次范围 + 调休 + 调课」四者叠加 | 这是课表类产品最容易出 bug 的地方，需要一组**固定的测试样例**（我会在写代码阶段产出）。 |
| R7 | **JSON 函数的平台可用性** | 若自定义周次用 JSON 集合（Q-A2 乙方案），查询依赖 SQLite 的 `json_each`。桌面/Web 端无问题，但 **Android 系统自带 SQLite 的版本与编译选项不一致**，可能不可用。规避方式二选一：① 打包自带 SQLite（增加体积）；② 改用**位图整数**（丙方案，已实测，不依赖 JSON 函数）。 |
| R8 | 时间戳与墙钟时间混用 | `created_at/updated_at` 建议用 UTC 毫秒（用于比较），而上课时间必须用**墙钟时间**（`08:00`）。两者绝不可混用；同步协议需明确区分，否则跨时区设备会算出错误的提醒时刻。 |
