单机单用户，本期仅 1 条记录；存在是为了将来接账号体系时不推翻结构。

```sql

  id          TEXT PRIMARY KEY,
  nickname    TEXT NOT NULL DEFAULT '我',
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);
```

### 2.3 `time_slots` 节次时间
✅ 决策：**节次数与时间可自定义**。

```sql
CREATE TABLE time_slots (
  id          TEXT PRIMARY KEY,
  semester_id TEXT NOT NULL REFERENCES semesters(id) ON DELETE CASCADE,
  period_no   INTEGER NOT NULL CHECK (period_no BETWEEN 1 AND 40),  -- 不写死上限
  start_time  TEXT NOT NULL,                 -- 'HH:MM'
  end_time    TEXT NOT NULL,                 -- 'HH:MM'
  label       TEXT,                          -- '第1-2节'
  section     TEXT CHECK (section IN ('am','pm','night')),  -- 上午/下午/晚上，可空
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE UNIQUE INDEX ux_time_slots ON time_slots(semester_id, period_no)
  WHERE deleted_at IS NULL;
CREATE INDEX ix_time_slots_semester ON time_slots(semester_id);
```

**说明**：一天实际几节**由 `time_slots` 的行数决定**，不写死在代码里（对应你「可自定义解析」的要求）。
`CHECK 1..40` 只是一个防脏数据的粗上界，不是业务上限。

⚠ 待确认：`section`（上午/下午/晚上）是**手动设置**，还是**按时间自动推断**（如 12:00 前为上午）？我倾向自动推断 + 允许手动覆盖。

### 2.4 `courses` 课程
✅ 决策：**加「学分」与「备注/短名」**；颜色存十六进制。

```sql
CREATE TABLE courses (
  id          TEXT PRIMARY KEY,

  deleted_at  INTEGER

CREATE INDEX ix_courses_semester ON courses(semester_id);
```

### 2.5 `course_schedules` 排课
✅ 决策：**「单独选择上哪几周」，并提供单双周快捷选项。**
即周次在**存储层就是一个周次集合**；「单双周」只是 UI/导入时的一个快捷选择，落到库里仍是具体周次。

```sql
CREATE TABLE course_schedules (
  id            TEXT PRIMARY KEY,
  course_id     TEXT NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  day_of_week   INTEGER NOT NULL CHECK (day_of_week BETWEEN 1 AND 7),  -- 1=周一
  period_start  INTEGER NOT NULL CHECK (period_start BETWEEN 1 AND 40),
  period_end    INTEGER NOT NULL CHECK (period_end   BETWEEN 1 AND 40),
  weeks_mask    INTEGER NOT NULL CHECK (weeks_mask > 0),  -- 位图：第 N 周 = 第 (N-1) 位
  weeks_raw     TEXT,                        -- 原始文本，如 '1-16周(单)'，用于显示与回导
  room          TEXT,                        -- 覆盖 courses.location
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER,
  CHECK (period_end >= period_start)
);

CREATE INDEX ix_schedules_course ON course_schedules(course_id);
CREATE INDEX ix_schedules_day    ON course_schedules(day_of_week);
```

**位图语义**（已实测，见 `records/M0-数据模型校验记录.md`）：

| 周次集合 | `weeks_mask` | 查询条件 |
|---|---|---|
| 第 1–16 周 | `2^16 - 1 = 65535` | `(weeks_mask >> (:week - 1)) & 1 = 1` |
| 单周 1–16 周 | 奇数位 | 同上，由写入时算好 |
| 双周 2–16 周 | 偶数位 | 同上 |
| 仅第 1/3/5/7 周 | `85` | 同上 |

**为什么用位图而不是 JSON**（风险 R7，已实测）：
`json_each` 依赖 SQLite 的 JSON 函数；桌面/Web 无问题，但 **Android 系统自带 SQLite 的版本与编译选项不一致**，不能假设可用。
位图查询 `(weeks_mask >> (:week - 1)) & 1 = 1` **不依赖任何特殊函数**，任何 SQLite 版本都能跑，且索引友好。

⚠ 待确认 Q-A2：**存储编码用位图（我推荐）还是 JSON 数组？** 语义已按你的决策定为「周次集合」，这里只是编码方式。

⚠ 待确认：
- Q：`weeks_raw`（保留教务原文）要不要？我倾向要——显示与「导出回教务格式」都用得上。
- Q：是否还需要一个「学期内所有周次」的快捷标记（如前 8 周 / 后 8 周）？属 UI 便利，不必入库。

### 2.7 `events` 日程（**本次最大变更**）
✅ 决策：**调课、调休、节假日全部塞进本表，不新建表。**
因此本表同时承载 7 种语义。为在单表内仍保住数据完整性，按 `type` 加了**条件 CHECK 约束**。

```sql
CREATE TABLE events (
  id               TEXT PRIMARY KEY,
  user_id          TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  semester_id      TEXT REFERENCES semesters(id) ON DELETE SET NULL,  -- 可脱离学期
  type             TEXT NOT NULL CHECK (type IN (
                     'exam',        -- 考试
                     'todo',        -- 待办
                     'temp',        -- 临时日程
                     'reschedule',  -- 调课（原课次改期/改教室/取消）
                     'holiday',     -- 放假（当天不排课）
                     'makeup',      -- 调休补课（当天按某星期上课）
                     'workday'      -- 明确为上课日（覆盖内置节假日）
                   )),
  title            TEXT NOT NULL,
  on_date          TEXT,      -- 针对的日期 'YYYY-MM-DD'：假期日/补课日/被调课的原上课日
  start_at         TEXT,      -- 考试与临时日程的开始时刻
  end_at           TEXT,
  all_day          INTEGER NOT NULL DEFAULT 0,
  location         TEXT,
  note             TEXT,
  done             INTEGER NOT NULL DEFAULT 0,           -- 待办完成
  -- 调课(type='reschedule')专用
  ref_schedule_id  TEXT REFERENCES course_schedules(id) ON DELETE CASCADE,
  action           TEXT CHECK (action IN ('move','cancel','room_change','add')),
  new_date         TEXT,
  new_period_start INTEGER CHECK (new_period_start BETWEEN 1 AND 40),
  new_period_end   INTEGER CHECK (new_period_end   BETWEEN 1 AND 40),
  new_room         TEXT,
  -- 调休(type IN holiday/makeup/workday)专用
  as_day_of_week   INTEGER CHECK (as_day_of_week BETWEEN 1 AND 7),
  source           TEXT CHECK (source IN ('builtin','manual','from_school')),  -- 节假日来源
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  deleted_at       INTEGER,

  -- 单表内的完整性约束：不同 type 必须有对应字段
  CHECK (type <> 'reschedule' OR (ref_schedule_id IS NOT NULL AND action IS NOT NULL)),
  CHECK (type <> 'reschedule' OR action <> 'move' OR new_date IS NOT NULL),
  CHECK (type NOT IN ('holiday','makeup','workday') OR on_date IS NOT NULL),
  CHECK (type <> 'makeup'      OR as_day_of_week IS NOT NULL),
  CHECK (type <> 'reschedule'  OR (new_period_end IS NULL OR new_period_start IS NOT NULL)),
  CHECK (new_period_end IS NULL OR new_period_start IS NULL OR new_period_end >= new_period_start)
);

CREATE INDEX ix_events_user_time ON events(user_id, start_at);
CREATE INDEX ix_events_semester  ON events(semester_id);
CREATE INDEX ix_events_type_date ON events(type, on_date);
-- 同一学期同一天只能有一条「假期/补课/上课日」定义
CREATE UNIQUE INDEX ux_events_day_kind
  ON events(semester_id, on_date)
  WHERE type IN ('holiday','makeup','workday') AND deleted_at IS NULL;
```

#### ⚠ 我必须如实告知的代价

你选择「不新建表」，我按你的决定实现了。但请知晓单表承载 7 种语义的**具体代价**：

| 代价 | 说明 | 我的缓解措施 |
|---|---|---|
| 大量可空字段 | 表宽 22 列，多数行只用其中一半 | 用 `CHECK` 按 type 强制必填字段，防止「半条数据」 |
| 语义靠 type 区分 | 查询必须带 type 条件，漏写会串数据 | 所有查询封装在数据访问层，禁止裸 SQL 拼装 |
| 唯一性约束复杂 | 「同一天只能一个假期定义」需部分唯一索引 | 已实测有效 |
| 将来扩展变难 | 再加一种日程类型要继续加可空字段 | 已记入风险 R9 |

**若你后续觉得难维护，改回独立表是一次纯迁移操作（数据可完整搬迁），不必现在决定。**

## 4. 关键查询（用来说明模型够用）

```sql
-- Q1. 第 N 周某天的课（周视图）
SELECT c.name, c.short_name, c.color, cs.period_start, cs.period_end,
       COALESCE(cs.room, c.location) AS room
FROM course_schedules cs
JOIN courses c ON c.id = cs.course_id
WHERE c.semester_id = :sid
  AND cs.day_of_week = :dow
  AND (cs.weeks_mask >> (:week - 1)) & 1 = 1     -- 位图判定，无需特殊函数
  AND cs.deleted_at IS NULL AND c.deleted_at IS NULL
ORDER BY cs.period_start;

-- Q2. 某天的调休/放假情况（提醒是否跳过 + 周视图覆盖）
SELECT type, as_day_of_week, source FROM events
WHERE semester_id = :sid AND on_date = :date
  AND type IN ('holiday','makeup','workday') AND deleted_at IS NULL;

-- Q3. 某次课的调课覆盖（改期/改教室/取消）
SELECT action, new_date, new_period_start, new_period_end, new_room FROM events
WHERE type = 'reschedule' AND ref_schedule_id = :schedule_id
  AND on_date = :original_date AND deleted_at IS NULL;

-- Q4. 「下一节课」（小组件）：需先由 semesters.start_date + time_slots 把
--     排课展开成具体课次，再与 now 比较 —— 见第 5 节的 expand 函数
```

## 5. 待你决定的一个架构问题

`course_schedules` 里没有「绝对时刻」，必须结合 `semesters.start_date` + `time_slots` 计算。
「下一节课」「提醒调度」「小组件」都要用，建议在应用层做**展开(expand)函数**：

```
expand(semester, date_range) -> [occurrence]
occurrence = { 日期, 第几节, 起止墙钟时间, 课程, 教室, 是否被调课/取消 }
```

并且第 2.7 节的 `events` 覆盖（放假/调休/调课）要**在这一层统一叠加**，保证课表、提醒、小组件三处结果一致。

⚠ 待确认：是否把展开结果**缓存落库**（换取查询速度，代价是失效逻辑）？我倾向**先不落库，纯函数展开**。

## 6. 风险清单（v2）

| # | 风险 | 说明 |
|---|---|---|
| R1 | 1 起算 vs 0 起算 | 全项目统一 1 起算，写进代码规范。位图第 N 周对应第 (N-1) 位，是最易错处，需专门单测。 |
| R2 | 时区 | 业务时刻存**墙钟时间**，时间戳存 **UTC 毫秒**，两者绝不可混用。 |
| R3 | 软删除 + 唯一索引 | 已实测：部分唯一索引按预期放行，无需额外规避。 |
| R4 | `reminders.target_id` 无外键 | 删除课程/日程须在应用层清理提醒，否则「幽灵提醒」。 |
| R5 | 提醒精确性依赖系统能力 | Android 14 精确闹钟默认被拒（课表类可申报 `USE_EXACT_ALARM`）；Windows 计划通知有 5 分钟投递窗口。详见 `02-技术选型对比.md`。 |
| R6 | 四者叠加 | 周次集合 + 调休 + 调课 + 时间 → 最易出 bug，必须用固定样例做单测。 |
| R7 | 位图编码的易错性 | 位运算容易写反（周 1 ↔ 第 0 位），需封装成一对 `set_week()/has_week()` 函数并单测。 |
| R8 | 时间戳与墙钟混用 | 同 R2。 |
| R9 | **单表 7 种语义的长期可维护性** | 决策所致（2.7 节）。缓解：CHECK 约束 + 数据访问层封装；若将来难维护，可纯迁移拆分。 |
| R10 | 节假日数据三来源冲突 | 「都做」（内置/手动/教务）时必须定义**优先级**，否则内置国庆假与教务校历打架。→ 见 Q-A7 追问。 |
