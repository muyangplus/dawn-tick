# 06 发布与版本

## 0. 构建纪律

- 只用 `tools/build-local.ps1` 产出交付件；**不得**用 `cargo build` 的产物替代，也不得从 `target` 目录手工拷贝 exe 充当交付件。
- 直接 `cargo build` 的产物按开发模式编译，窗口会去加载 `devUrl`（`http://localhost:5173`），运行后表现为「localhost 拒绝连接」。
- 打包脚本会校验产物是否嵌入了前端哈希资源名，未嵌入则直接报错。

## 1. 渠道

| 渠道 | 来源分支 | 发布方式 | 标签 | Release 标记 | 构建类型 |
|---|---|---|---|---|---|
| dev | `dev` | 推送 `dev` 自动滚动覆盖（也支持手动/定时） | 固定 `dev-latest` | 预发布 | debug（Windows `--debug`、Android `assembleDebug`） |
| beta | `main` | 在 `main` 上打 `vX.Y.Z-beta.<n>` 标签触发，保留历史 | `vX.Y.Z-beta.<n>` | 预发布 | release |
| release | `main` | 在 `main` 上打 `vX.Y.Z` 标签触发，自动发布 | `vX.Y.Z` | 正式 Release | release |

开发流程：改动只在 `dev` 上做，每次推送 `dev` 自动发布 `dev-latest`（滚动覆盖），`dev` 通过 PR 合入 `main`；`main` 是 beta 与 release 的唯一发版来源（没有 `beta` 分支）。CI 在 push 到 `dev`、`main` 与打标签时运行。

三端均写入统一日志：启动与崩溃、教务登录全过程、数据读写与同步；日志不含明文密码与密文，可在设置页导出。

Windows 侧数据目录：安装版在 `%APPDATA%\com.dawntick.app`，便携版（可执行文件名为 `DawnTick.exe` 且不在 `%LOCALAPPDATA%\DawnTick` 下）在程序所在目录；数据库与日志在该目录内，窗口几何存在数据库的 `app_meta.window_geometry` 里（启动时在窗口显示前读出来应用），WebView2 用户数据目录固定在 `%LOCALAPPDATA%\com.dawntick.app\EBWebView`（首次运行把旧的 `<数据目录>\EBWebView` 整体搬过去，搬不动就继续用旧位置）；设置页「数据」可填自定义位置（留空用默认，相对路径相对程序目录），改完重启生效。数据库日志模式由「启用 WAL 日志模式」开关决定：默认便携版关闭（`journal_mode=DELETE`，数据库为单个文件）、安装版开启；关闭后不再产生 `-wal` / `-shm`。日志同时输出到控制台：从终端启动时输出到该终端，提权启动时先附加父控制台、无法附加则另开一个日志控制台；数据目录不可写时依次回退 `%LOCALAPPDATA%\com.dawntick.app` 与 `%TEMP%\DawnTick`。日志行为 `YYYY-MM-DD HH:MM:SS.mmm ±HH:MM [level] scope: 消息`，文件、控制台与「导出日志」同一格式。设置页的「打开数据目录」与「打开日志文件所在目录」在资源管理器中定位对应目录。

备份：Windows 用 `VACUUM INTO` 把整库写成 `backups/dawn-tick-<yyyyMMdd-HHmmss>.db`，Web 与 Android 把 JSON 快照写进库内；总开关加「启动时」「每天」两个开关，保留份数可设 1–100（默认 10），超出自动删最旧。「设备与同步」页列快照可查看、恢复、删除；恢复文件快照时先在 `pending-restore.json` 排队，重启时在打开数据库之前覆盖，恢复前自动备一份当前库。跨设备迁移用「设备与同步」页的导出与导入：JSON 文件、Base64 文本或整包 zip（可选同时打包预设快照与日志），导入冲突处理为跳过 / 覆盖 / 清空所选模块后导入 / 按修改时间合并。

WebDAV 同步：把整库快照与设置预设打成一个 zip 放到远端目录，固定名 `DawnTick-backup.zip` 覆盖，也可按「远端保留历史多份」改成带时间戳的多份。地址填完整目录 URL，用户名与密码存在本机设置里（密码不参与导出）。自动同步分「启动时」与「每天」两个开关：先比远端 `Last-Modified` 与上次上传时间，远端更新就提示下载（下载前自动备份本机，可选「恢复全部」或「只应用设置与预设」），否则上传；只上传、不自动下载。Windows 用 Tauri 官方 http 插件发请求（不受 WebView 的 CORS 限制），Android 由 Capacitor 的原生 HTTP 接管 fetch，Web 走浏览器 fetch（需服务端允许跨域）。

第三方依赖的清单与许可证全文写在仓库根目录 `THIRD-PARTY-LICENSES.md`，由 `node tools/legal/collect-licenses.mjs` 从各端清单与已安装依赖的元数据生成；`--check` 校验磁盘内容与依赖一致，不一致退出码 1。应用内「关于」展示同一份清单。

桌面小组件在手机端设置页「外观」卡给出添加引导：每个尺寸一个「添加到桌面」按钮，走 Capacitor 插件 `DawnTickWidget.requestPin`（Android `requestPinAppWidget`）。插件按系统回调区分结果：`added`（已添加）、`already-added`（桌面上已有）、`cancelled`（没收到确认，含用户取消与启动器没弹窗）、`unsupported`（系统版本低于 Android 8 或启动器不支持一键添加）、`disabled`（组件被系统停用）、`rejected`（系统没接受请求）；设置页按结果给手动添加或去系统设置的下一步，并显示每种尺寸是否已在桌面上。Windows 端只显示悬浮窗设置（`悬浮窗` 与 `悬浮窗样式`），手机端不显示这两项。

安卓通知状态由 `SystemActions.notificationStatus` 读原生：应用级通知开关（`areNotificationsEnabled`）、Android 13+ 的 `POST_NOTIFICATIONS` 运行时权限、以及课前提醒所在通知渠道是否被静音；「未申请 / 已拒绝 / 永久拒绝」靠 `app_meta.notify_permission_asked` 是否申请过配合 `shouldShowRequestPermissionRationale` 判断。设置页「提醒设置」按状态给「重新申请通知权限」或「去系统设置开启」，静音时直达渠道设置页。

客户端检查更新按渠道读取 `api.github.com` 的发布接口：dev 查滚动标签 `dev-latest`，release 查最新正式版，beta 查发布列表（`releases?per_page=30`）——从最近的发布里取「最新的 beta 预发布（`vX.Y.Z-beta.N`）」与「最新的正式版」中版本更高的那个（正式版发布后测试版用户也能直接更到正式版），打开「接收测试版更新」的正式版用户走同一套；失败时回退发布内的 `version.json`：dev 读 `dev-latest` 的直连资产，release 读 `/releases/latest/download/version.json`，beta 的标签带版本号、没有固定直连地址，只查发布列表。预设更新先取 `raw.githubusercontent.com`，失败时回退 `api.github.com` 的 contents 接口。两条链路都不使用第三方镜像。设置页「更新与维护」展示检查结果、预设版本与运行权限；「自动检查版本更新」默认开启，启动后自动查一次，发现新版本时弹窗显示版本、渠道与发布说明。

渠道提示：dev 与 beta 各自有一条首次提示（开发版可能频繁更新、测试版可能不稳定），已读记录写在 `app_meta.seen_notices`，按提示 id 记录——不是初次使用但没提示过这条信息也会弹。切到测试版后自动再检查一次更新。

`publish.yml` 的 dev 渠道在构建前比对 `dev-latest` 发布正文里的「提交 <sha>」与本次 `GITHUB_SHA`，相同则整个流水线跳过（`skip=true`，其余 job 带 `if: needs.plan.outputs.skip != 'true'`），定时任务不会重复构建没有新提交的版本。

### 1.1 渠道功能差异

| 功能 | 可见渠道 | 说明 |
|---|---|---|
| 日志导出与诊断信息 | dev、beta | 正式版隐藏入口，日志仍会写入本地文件 |

登记的唯一位置为 `apps/web/src/channel.ts` 的 `FEATURES`；构建时由 `DT_CHANNEL` 注入，本地与 CI 默认 `dev`，发布工作流按渠道注入。关于页显示版本与渠道。

### 1.2 数据库迁移

`packages/core/src/schema/` 下的迁移按 id 升序应用，各端一致：`001_init` 建表，`002_event_kinds` 扩充事件表（作业 / 实验类型与逐条开关，按「改名 → 建新表 → 拷数据 → 删旧表」重建），`003_custom_time` 为事件与排课加自定义时间列，`004_timetable_entries` 加「是否显示在课表上」并把实验回填为显示，`005_due_at_any` 放开截止时刻（所有条目类型都能带 `due_at`）。Windows 侧由 `tauri-plugin-sql` 按版本号应用，Web / Android 侧每次启动都调用 `migrate`（已应用的会跳过）。

已发布的迁移文件不得再修改：`tauri-plugin-sql` 记录已应用迁移的校验和，改动历史文件会让老库启动失败。新增结构一律追加新迁移。

## 2. 版本号

| 位置 | 字段 | 写入方 |
|---|---|---|
| `package.json` | `version` | 唯一来源，手工修改 |
| `apps/web/package.json` | `version` | `tools/release/version.mjs` |
| `apps/desktop/src-tauri/tauri.conf.json` | `version` | `tools/release/version.mjs` |
| `apps/desktop/src-tauri/Cargo.toml` | `[package] version` | `tools/release/version.mjs` |
| `apps/mobile/android/app/build.gradle` | `versionName` / `versionCode` | `tools/release/version.mjs`，`versionCode = major*10000 + minor*100 + patch` |

升版判定（语义化版本，`0.y.z` 阶段以「有行为变更」为界）：

| 改动 | 升哪一位 | 例子 |
|---|---|---|
| 用户可见的行为变更、新功能、界面或数据语义调整 | minor | 周视图列语义改为「今天起的 N 天」、新增 WebDAV 同步 |
| 仅修复与优化，行为对使用者不变 | patch | 修「回到今天」不生效、小组件行数算错 |
| 破坏兼容（数据结构不兼容、需手动迁移、旧版本无法读新库） | major | 老库在不做迁移脚本的前提下无法打开 |

升版命令：`node tools/release/version.mjs 0.2.0`（同时写五处）；`node tools/release/version.mjs --check` 校验一致，不一致退出码 1。

## 2.1 变更日志

`CHANGELOG.md`（仓库根目录）按 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 维护，小节固定为「新增 / 变更 / 修复 / 移除」，版本从新到旧、已发布条目带日期与底部比较链接。

- 开发期：改动只写进 `## [未发布]` 段，提交时按「新增 / 变更 / 修复」归类，写「用户能感知到什么」而不是提交标题。
- 发版时：把 `## [未发布]` 标题改成 `## [<版本>] - <YYYY-MM-DD>`，补底部比较链接，再把 `## [未发布]` 空段留在最上面，最后打标签。
- 取段落：`node tools/release/changelog.mjs --extract=<版本>` 打印该版本正文（找不到退出码 1）；`--extract` 不带参数取「未发布」段；`--check` 校验结构。
- 发布工作流用该段落作为 Release 正文（正文首行仍是 `渠道 … · 来源 … · 提交 …`，客户端从这里读提交号）；段落缺失时回退 `--generate-notes`。

## 3. 触发

| 事件 | 渠道 | 构建自 | 行为 |
|---|---|---|---|
| 推送分支 `dev` | dev | `dev` | 删除并重建 `dev-latest`（自动） |
| 打标签 `vX.Y.Z` | release | 该标签 | 创建正式 Release |
| 打标签 `vX.Y.Z-beta.N` | beta | 该标签 | 创建 beta 预发布 |
| 手动触发（选 dev） | dev | `dev` | 删除并重建 `dev-latest` |
| 手动触发（选 beta） | beta | `main` | 标签续号 `vX.Y.Z-beta.<n>` |
| 手动触发（选 release） | release | `main` | 按当前版本号发布 |
| 定时（每天 UTC 01:00） | dev | `dev` | 同手动 dev（作为兜底） |

push 到 `dev`、`main` 不触发发版，只触发 CI。

发布前置：发版工作流先执行 `gate` 任务，按构建引用解析出提交，再轮询该提交上的 `ci.yml` 运行结果。成功才继续构建；失败或无记录（等待上限 40 分钟）则中止。CI 不重复运行：`ci.yml` 已监听 `v*` 标签，其并发键为「分支-提交号」，同一提交上只跑一次检查。

## 4. 产物

产物文件名使用 ASCII 与英文名 `DawnTick`：GitHub 会剥离 Release 产物名中的非 ASCII 字符（实测上传 `晓刻-测试.txt` 得到 `-.txt`），中文名保留在 Release 标题。所有产物（含 `version.json`）的 SHA256 统一写进发布里的 `SHA256SUMS.txt`（`sha256sum *` 格式），不再逐个附 `.sha256`。

| 文件 | 来源 |
|---|---|
| `DawnTick-<version>-<channel>-windows-x64-setup.exe` | `tauri build` 的 NSIS 安装包 |
| `DawnTick-<version>-<channel>-windows-x64-portable.zip` | `tauri build` 的独立 exe，包内为 `DawnTick.exe` |
| `DawnTick-<version>-<channel>-android.apk` | dev 为 `assembleDebug`、其余渠道为 `assembleRelease`（都有签名材料时用同一把正式密钥） |
| `DawnTick-<version>-<channel>-web.zip` | `apps/web/dist` |
| `version.json` | 发布步骤生成：渠道、版本、标签、发布说明与产物名，客户端更新兜底清单 |
| `SHA256SUMS.txt` | 全部产物的 SHA256（`sha256sum` 文本） |

dev 渠道的 `<version>` 带构建时间戳（`yyyyMMddHHmm`，本地时间），例如 `DawnTick-0.1.0.202510131430-dev-android.apk`；beta 与 release 保持 `X.Y.Z`。时间戳只用于区分构建，不参与版本比较（`compareVersions` 只比 `major.minor.patch`），所以本地 dev 构建不会因时间戳被判成「有新版本」。Android 的 versionCode 取 2024-01-01 起的分钟数，随时间单调递增，dev / beta / release 互相覆盖安装都不会被判成降级。

Android 的 dev 构建在提供签名材料时同样使用正式密钥签名：材料来自环境变量 `ANDROID_KEYSTORE_PATH` / `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD`，本地也可写在 `apps/mobile/android/keystore.properties` 或 `<仓库根>/keys/keystore.properties`（两处都在 .gitignore 内，键名两种写法都认）。同一把密钥才能覆盖安装；若旧安装是调试密钥签的，需要先卸载一次。

仓库 secret 的配置（需要 `gh` 已登录且对该仓库有 secrets 写权限）：

```powershell
gh auth login
powershell -ExecutionPolicy Bypass -File tools/release/set-github-secrets.ps1
```

脚本从 `keys/keystore.properties` 取材料，写入 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD` 四个 secret，只打印 secret 名与字节数，不回显口令。`ANDROID_KEYSTORE_BASE64` 是密钥库文件的单行 base64（`[Convert]::ToBase64String([IO.File]::ReadAllBytes($jks))`），`publish.yml` 的 Android job 会把它解回 `$RUNNER_TEMP/release.key` 后交给 Gradle。

发布说明：自动生成，并按渠道指定比较基准。滚动标签会移动，三个渠道的比较基准都排除 `*-latest`。工作流校验里有这条断言（`tools/verify/check-workflows.py` 的 `PUBLISH_NOTES_REQUIRED`）。

用 CHANGELOG 段落作 Release 正文时，GitHub 不会自动补比较链接；工作流按上表基准在正文末尾追加 `**Full Changelog**: compare/<基准>...<标签>`。滚动标签已从上表基准中排除，未取到基准时只留正文。

| 渠道 | 比较基准 | 说明头部 |
|---|---|---|
| dev | 最近一个非 `dev-latest` 的发布 | `渠道 dev · 来源 dev · 提交 <sha>` |
| beta | 最近一个 `-beta.` 发布 | `渠道 beta · 来源 beta · 提交 <sha>` |
| release | 最近一个正式发布 | `渠道 release · 来源 main · 提交 <sha>` |

定时任务的执行细节：GitHub 的 `schedule` 只读取默认分支的工作流文件，因此定时任务实际用的是 `main` 上的 `publish.yml`；该任务会先检出 `dev`，使版本号与标签规则取自 `dev`。工作流结构本身的改动需合并到 `main` 才对定时任务生效。
